i18n 통합 기준 최종본 (글로벌 초대장 프로젝트)

> Product Mode (`ko-KR` / `en-US` 서비스 모드) 정의는 [`docs/LOCALE_PRODUCT_ARCHITECTURE.md`](./LOCALE_PRODUCT_ARCHITECTURE.md) 를 따른다.
> 이 문서는 dictionary / key / `t()` 규칙 SSOT 다.

0. 목표

하드코딩 문자열을 구조적으로 차단한다.

i18n 관련 정의(키/타입/리소스/헬퍼)를 한 루트에 모아 단일 기준(Single Source of Truth)으로 운영한다.

변경 지점을 최소화해 추가/수정이 항상 같은 위치에서 발생하도록 강제한다.

1. 단일 기준 경로 (Single Source of Truth)
✅ i18n 루트는 오직 하나

기준 루트: frontend/src/i18n/

이 프로젝트에서 i18n은 반드시 이 폴더 아래에만 존재해야 한다.

2. 표준 폴더 구조 (권장 고정안)
frontend/
└─ src/
   └─ i18n/
      ├─ keys.ts           # I18N_KEYS (as const) - 모든 키의 유일한 정의
      ├─ types.ts          # Text/I18nText 등 의미 구분 타입
      ├─ index.ts          # 외부 노출용 엔트리 (re-export)
      ├─ t.ts              # (선택) translate helper / wrapper
      └─ locales/
         ├─ ko.ts
         ├─ en.ts
         ├─ mn.ts
         └─ ja.ts          # 필요 국가 확장
docs/
└─ i18n.md                 # 규칙/추가 방법/금지 패턴 문서

3. 변경 지점 최소화 원칙
✅ 키 추가/수정은 여기만

frontend/src/i18n/keys.ts

docs/i18n.md (규칙 문서 동기화)

✅ 번역 리소스 추가/수정은 여기만

frontend/src/i18n/locales/*.ts

“새 문구 추가”는 keys.ts에 키 추가 → locales에 번역 추가 → 문서에 규칙 준수 확인
이 3단계로 고정한다.

4. 키 정의 정책 (엄격)
✅ I18N_KEYS는 반드시 as const

키는 리터럴 타입으로 고정해서 오타/누락을 컴파일 단계에서 차단한다.

키 접근은 반드시 I18N_KEYS.xxx 형태로 한다. ("home.title" 같은 문자열 직접 입력 금지)

4-1. 네이밍 규칙 (필수)
- `share.*`
- `invitation.*`
- `message.*`
- `relationship.*`

5. 타입 정책 (유연 + 의미 구분)

타입은 런타임 비용 없이 의미만 구분한다.

“문자열”과 “i18n 키 기반 텍스트”를 구분할 수 있어야 한다.

단, 타입 추상화로 개발 속도를 해치지 않도록 필요 최소만 유지한다.

6. 금지 규칙 (프로젝트 레벨)
❌ UI에서 하드코딩 문자열 직접 사용 금지

버튼/라벨/토스트/빈 상태 문구/에러 문구 등 사용자 노출 텍스트는 모두 i18n 키를 통해야 한다.

예외: 디버그 로그/개발용 콘솔 메시지는 허용(단, 사용자 노출 금지)

❌ i18n 키 정의 중복 금지

keys.ts가 아닌 곳에서 키를 재정의하거나 별도 key map을 만드는 행위를 금지한다.

❌ i18n 타입/헬퍼 분산 금지

src/types/text.ts 같은 “i18n 관련 타입 분산”은 통합 후 금지한다.

7. 기존 중복 파일 처리 원칙 (안전/정석)

현재 중복 가능성이 있는 경로:

frontend/src/i18n/keys.ts (기존)

frontend/src/types/text.ts (기존)

✅ 정석 통합 원칙

외부 import가 깨지지 않도록 “기존 경로를 유지”하면서 내부를 새 기준으로 흡수한다.

최종적으로는 frontend/src/i18n/ 아래로 개념을 모으고, index.ts를 통해 재노출(re-export)한다.

즉, “대규모 전수 수정”이 아니라
기존 코드 안정성 유지 + 내부 코어만 단일화가 목표.

8. 완료 기준 (Acceptance Criteria)

이 기준을 만족하면 “통합 1단계 완료”로 본다.

 i18n 루트가 frontend/src/i18n/로 확정되어 문서에 명시됨

 I18N_KEYS가 단일 파일에서 as const로 관리됨

 새 텍스트 추가 절차가 “keys/locales/docs” 3단계로 고정됨

 중복 파일이 존재하더라도 “단일 기준”이 무엇인지 팀이 혼동하지 않게 됨

 이후 리팩터링은 “점진 적용”으로 진행 가능(전수 수정 금지)

9. 운영 원칙 (팀 룰)

신규 기능/컴포넌트는 무조건 새 i18n 규칙으로만 추가한다.

기존 컴포넌트는 “수정이 발생할 때” 해당 범위만 점진적으로 i18n 치환한다.

버튼

제목

에러/알림 문구

❌ JSX, TS, 상수 파일 어디에서도 문자열 직접 작성 금지

2. 기본 사용 패턴 (정상)
2-1. 컴포넌트에서 텍스트 출력
import { t } from '@/i18n/t';
import { I18N_KEYS } from '@/i18n';

export function SubmitButton() {
  return (
    <button>
      {t(I18N_KEYS.common.submit)}
    </button>
  );
}


✔ 키는 반드시 I18N_KEYS.xxx 형태
✔ 문자열 직접 입력 없음

2-2. props로 텍스트를 넘길 때
<MyModal
  title={t(I18N_KEYS.modal.confirm.title)}
  description={t(I18N_KEYS.modal.confirm.description)}
/>


✔ 부모에서 번역 → 자식은 string만 받음
✔ 자식 컴포넌트는 i18n을 모르게 설계 가능

2-3. 리스트 / 템플릿 이름
{templates.map(tpl => (
  <li key={tpl.id}>
    {t(I18N_KEYS.template[tpl.code].name)}
  </li>
))}


✔ flat key + 네임스페이스 구조 유지
✔ template.X.name 형태 보장

3. 신규 키 추가 절차 (고정 루트)

STEP 2️⃣ locales/*.ts
export default {
